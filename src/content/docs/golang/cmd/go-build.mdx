## go build について

再利用できるように実行形式のバイナリファイルを作りたい場合は `go build` コマンドを使用します。

```bash frame=none
go build hello.go
```

これを実行することで、hello (windows の場合は hello.exe) という実行形式のバイナリファイルが作成されます。
このファイルを実行するには `./hello` とします。
バイナリファイルは `go run` コマンドでは実行できません。

```bash frame=none
# バイナリファイルを実行
./hello
Hello World
2025-01-18 14:14:55.655597 +0900 JST m=+0.000276751

# go run では実行できない
go run ./main
go: cannot find main module, but found .git/config in /Users/t_inoue/Documents/01_ProjectsApp/11_Practices/12_Golang_try
        to create a module there, run:
        go mod init
```

バイナリファイルの名前は指定したファイル名、ディレクトリ名、パッケージ名によって決定されます。
変更したい場合は `-o` フラグを使用します。

```bash frame=none
go build -o myapp hello.go
```

:::tip[バイナリファイルの名前]

`go build` を使うことで他人に使ってもらえる実行形式ファイルを作成できる。
フラグ `-o` を使用することでバイナリファイルの名前を指定してわかりやすい名前にすることができる。

:::

### syntax

```bash frame=none
go build [-o output] [build flags] [packages]
```

Build はインポートパスで指定されたパッケージを依存関係と共にコンパイルしますが、結果をインストールはしません。

build コマンドの引数が単一のディレクトリからの .go ファイルのリストである場合、
build はそれらを単一のパッケージを指定するソースファイルのリストとして扱います。

パッケージをコンパイルする際、build は `_test.go` で終わるファイルを無視します。

単一の main パッケージをコンパイルする場合、build は
最初のソースファイル名（`go build ed.go rx.go` は 'ed' または 'ed.exe' を出力）
またはソースコードディレクトリ名（'go build unix/sam' は 'sam' または 'sam.exe' を出力）
に基づいて実行可能ファイルを出力します。
Windows 実行可能ファイルを出力する場合は `.exe` サフィックスが追加されます。

複数のパッケージまたは単一の非 main パッケージをコンパイルする場合、
build はパッケージをコンパイルしますが、結果のオブジェクトは破棄され、
パッケージがビルド可能かどうかのチェックとしてのみ機能します。

-o フラグを使用すると、前述の 2 つの段落で説明したデフォルトの動作の代わりに、
指定された出力ファイルまたはディレクトリに実行可能ファイルやオブジェクトを
強制的に書き込みます。指定された出力が既存のディレクトリであるか、
スラッシュまたはバックスラッシュで終わる場合、生成された実行可能ファイルは
そのディレクトリに書き込まれます。

`-asmflags`、`-gccgoflags` 、`-gcflags` 、および `-ldflags` フラグは、ビルド中に基盤となるツールに渡すスペース区切りの引数リストを受け取ります。
リスト内の要素にスペースを埋め込みたい場合は、シングルクォートまたはダブルクォートで囲みます。
引数リストの前には、パッケージパターンと等号が付くことがあり、これによりそのパッケージパターンに一致するパッケージのビルドにのみその引数リストの使用が制限されます（パッケージパターンの説明については「go help packages」を参照してください）。
パターンなしでは、引数リストはコマンドラインで指定されたパッケージのみに適用されます。
フラグは異なるパターンで繰り返し使用することができ、異なるパッケージセットに対して異なる引数を指定できます。
パッケージが複数のフラグで指定されたパターンに一致する場合、コマンドラインで後に現れたフラグの一致が優先されます。
例えば、`go build -gcflags=-S fmt` はパッケージ fmt のみの逆アセンブルを出力しますが、`go build -gcflags=all=-S fmt` は fmt およびその依存関係すべての逆アセンブルを出力します。

パッケージの指定方法の詳細については「go help packages」を参照してください。
パッケージとバイナリがどこにインストールされるかの詳細については「go help gopath」を実行してください。
Go と C/C++間の呼び出し方法の詳細については「go help c」を実行してください。

注意: Build は「go help gopath」で説明されているような特定の規約に従います。しかし、すべてのプロジェクトがこれらの規約に従えるわけではありません。
独自の規約を持っていたり、別のソフトウェアビルドシステムを使用しているインストールでは、ビルドツールのオーバーヘッドや設計上の決定を避けるために、「go tool compile」や「go tool link」のような低レベルの呼び出しを選択する場合があります。

関連項目: go install, go get, go clean.

1. スペース区切りの引数リスト:
   フラグはスペースで区切られた引数リストを受け入れます。引数にスペースを含めたい場合は、シングルクォートまたはダブルクォートで囲む必要があります。

1. パッケージパターンの指定:
   引数リストの前にパッケージパターンを指定することができ、これにより特定のパッケージにのみその引数が適用されます。
   パターンが指定されていない場合、引数はコマンドラインで指定されたパッケージにのみ適用されます。

1. フラグの優先順位:
   同じパッケージに対して複数のフラグが適用される場合、コマンドラインで後に指定されたフラグが優先されます。

1. 具体例:

   - `go build -gcflags=-S fmt`: パッケージ fmt のみの逆アセンブルを出力します。
   - `go build -gcflags=all=-S fmt`: パッケージ fmt およびその依存関係すべての逆アセンブルを出力します。

1. 関連コマンドの案内:
   パッケージの指定方法やインストール先、Go と C/C++間の呼び出し方法についての追加情報は、各種 go help コマンドを参照するよう案内しています。

1. ビルドの規約と柔軟性:
   go build は特定の規約に従いますが、すべてのプロジェクトがこれに従うわけではないため、低レベルのツールを直接使用する選択肢も提供されています。
