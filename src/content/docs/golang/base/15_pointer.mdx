## ポインタ

ポインタは、メモリアドレスを指す変数です。ポインタを正しく使うことで、Go プログラムがより高速に効率よく動作させることができます。

<LinkPreview url="https://qiita.com/hiroaki-u/items/da7694ecffccbb49a139" />

### ポインタの入門

ポインタとは、ある値が保存されているメモリ内の位置を表す変数です。
次のコードにより変数がメモリに保存される様子を示しました。

```go
var x int32 = 10
var y bool = true
```

これを図にすると次のようになります。

どの変数も、1 バイトもしくは何バイトか連続したメモリに保存されており、その位置のことをアドレスといいます。
変数の型が違えば、保存時に必要なメモリの量も異なります。
上記の例では、`int32` 型の変数 `x` は 4 バイト分のメモリを占有しています。
`bool` 型の変数 `y` は 1 バイト分のメモリを占有しています。

このように、変数の型によって必要なメモリの量が異なるため、変数の型によってアドレスの位置も異なります。
4 バイトを占有するということは 1 〜 4 のアドレスに保存され、y の 1 バイトは 5 のアドレスに保存されています。
ポインタは、通常の変数と同じ「箱」ですが、その中に入っている「値」が数値や文字列などではなく、別の変数（別の箱）が置かれている場所（メモリ上のアドレス）そのものを示しています。

:::tip[通常の変数とポインタの違い]

**通常の変数**

変数 A に数値 10 が入っているなら、A は「10」という直接の値を持っています。

**ポインタ変数**

一方、ポインタ変数 B は、「A がどこにあるか」という情報、つまり A のメモリアドレス（例：0x7ffeeb3ff618 など）を持っています。
このため、B に「アクセスする」と、A の値 (10) にたどり着くことができるのです。
この仕組みにより、プログラムはアドレスを介して間接的にデータにアクセスでき、効率的なメモリ管理やデータの共有が可能になります。

:::

```go
var x int32 = 10
var y bool = true

pointerX := &x
pointerY := &y

var pointerZ *string
```

変数の型が違うと、保存に利用するメモリはその方に応じた容量になりますが、ポインタは常に同じサイズになります。
変数の容量ではなく、メモリ内での格納位置を示すためのメモリの量になるということです。
x へのポインタである `pointerX` はアドレス 6 に保存され、値は `0001` となっていますが、これが x のメモリアドレスを示しています。
となると、`pointerY` は `0005` となり、y のメモリアドレスを示しています。
`pointerZ` は `0000` となり、まだ値がなにも参照していないことを示しています。

## ポインタの宣言

Go のポインタの構文は C や C++ から一部借用していますが、Go にはガベージコレクタがあるため、メモリ管理ははるかに簡単です。ポインタに関する演算、C や C++ で可能なポインタの操作はできません。

### アドレス演算子とデリファレンス

#### アドレス演算子 `&変数`

`&` はアドレス演算子です。変数の前につけるとその変数のアドレスを返します。
返された値はポインタ型の値になります。

```go
x := 10
pointerX := &x
// ポインタ型の値を確認
fmt.Println(pointerX) // 0xc000012070
```

#### デリファレンス(逆参照) `*ポインタ変数`

参照しているアドレス情報をもとに、格納されている値を見るには `*` を変数名の前につけて宣言します。
`*ポインタ変数` として出力結果を確認することができます。(デリファレンス)

```go
fmt.Println(*pointerX) // 10
```

このようにして、変数の参照アドレスや、ポインタが参照するデータを取得して確認します。

ポインタのデフォルト値は `nil` です。
nil ポインタ (アドレス 0) のデリファレンスを試みると、実行時エラーが発生します。そのため、デリファレンスを行う前に nil ポインタかどうかを確認する必要があります。

```go
var pointerZ *string
fmt.Println(*pointerZ) // panic: runtime error: invalid memory address or nil pointer dereference
```

### ポインタの変数を宣言する

ポインタの変数を宣言するには、そのポインタが指すアドレスに保存されている変数の型を指定し、その型名の前に`*` をつけて宣言します。

```go
x := 10
var pointerToX *int32 = &x
```

組み込み関数 new はポインタ型の変数を生成します。指定された型でゼロ値を値とするインスタンスへのポインタを返します。

```go showLineNumbers {2-4}
pointerToX := new(int32)
fmt.Println(pointerToX) // 0xc000012070
fmt.Println(pointerToX == nil) // false
fmt.Println(*pointerToX) // 0
```

<Steps>

1. `fmt.Println(pointerToX)` は `pointerToX` 自体ののアドレスを出力します。

1. `fmt.Println(pointerToX == nil)` は `pointerToX` の初期値が nil かどうか確認しています。`nil ` の場合は panic が発生するため、new 関数での生成が、nil ではないことを確認できます。(`false` が出力されている。)

1. `fmt.Println(*pointerToX)` は `pointerToX` が指すアドレスに保存されている値を出力します。これは new 関数で生成した `int32` 型のゼロ値である `0` が出力されています。

</Steps>

ただし、関数 new はほとんど使われません。

構造体については、構造体リテラルの前に `&` をつけることでポインタを生成することができます。

```go
pointerToStruct := &struct {
	Field1 string
	Field2 int
}{"Hello", 10}

fmt.Println(pointerToStruct) // &{Hello 10}
```

#### 基本型のリテラルや定数にはアドレスがない

数値やブール値、文字列のリテラルは、コンパイル時に評価される定数のようなものです。これらは実行時にメモリ上に「変数」として確保されないため、直接その値のアドレス（メモリ位置）を取ることができません。つまり、たとえば `&10` や `&"Hello"` はエラーになります。

基本型へのポインタが必要な場合は、まず基本型の変数を宣言し、それからそれを参照するポインタ変数を宣言します。

```go
var y string // 基本型の変数 `y` を宣言
z := &y // string へのポインタ
```

<Steps>

1. ポインタとして扱うには、まず基本型のリテラルを変数に代入(基本型の変数 `y` を宣言します。)

1. 次に、その変数のメモリ上での位置を `&` 演算子で取得する必要があります。`y` のアドレスを参照するポインタ変数 `z` を宣言します。

</Steps>

構造体のフィールドに基本型へのポインタが定義されている場合は、そのフィールドにリテラルを直接代入できません。

```go showLineNumbers {3,9}
type person struct {
	FirstName  string
	MiddleName *string
	LastName   string
}

p := person{
	FirstName:  "Pat",
	MiddleName: "Perry", //cannot use "Perry" (untyped string constant) as *string value in struct literal
	LastName:   "Peterson",
}

fmt.Println(p)
```

<Steps>

1. フィールド `MiddleName` は `string` へのポインタです。(`*string` 型なので、値ではなくアドレスが必要)

1. このフィールドに直接リテラルを代入するとエラーになります。("Perry" はリテラルであり、実行時に変数として確保されないため、直接アドレスを取れません。)

</Steps>

この問題を回避する方法は 2 つあります。
一つは、定数値を保持する変数を作ることです。

```go
middle := "Perry"
p := person{
  FirstName:  "Pat",
  MiddleName: &middle,
  LastName:   "Peterson",
}
fmt.Println(p)
```

もう一つは、ブール値、数値、文字列を引数に取り、ポインタを返すヘルバー関数を作成することです。

```go
func stringp(s string) *string {
	return &s
}

func main() {
	type person struct {
		FirstName  string
		MiddleName *string
		LastName   string
	}

	p := person{
		FirstName:  "Pat",
		MiddleName: stringp("Perry"),
		LastName:   "Peterson",
	}
	fmt.Println(p)
}
```

定数 "Perry" が 関数 `stringp` に渡されると、その定数は引数にコピーされますが、引数とは関数内で、変数として扱われます。
変数であれば、メモリ内にアドレスがあります(メモリ上にローカル変数 `s` が存在する)。関数はその変数のメモリアドレスを `&s` で返すのです。これにより、`*string` 型の値を構造体に設定することができます。

## ポインタを恐れる必要はない

Java、JavaScript、Python、Ruby ... などの言語では、ポインタを意識せずにプログラムを書くことができます。そのため、ポインタという謎のものに苦手意識を持つ人が多いです。しかし、いずれの言語の「クラス」の裏側ではポインタが使われています。
Java や JavaScript では、基本型とクラスの間に振る舞いの違いがあります。(Python と Ruby には基本型でなく、イミュータブルなインスタンスで基本型をシミュレートしています。)
基本型の値が変数に代入されたり関数やメソッドに渡された場合、その先で行われた変更は元の値には反映されません。

いずれも以下の動きを持っています。

<Steps>
1.  `inner1` で、引数として渡されたクラスのインスタンス `x` を関数に渡して、その関数内で渡されてインスタンスのプロパティに 20 を代入すると、元のオブジェクトが変更される。
    `outer` と `f` と `inner1` の `f` は同じメモリを参照していますから、`inner1` 内で `f` のフィールドに対して行われた変更は `outer` 内の `f` に反映されます。

1. `inner2` で、渡されたパラメータとしてインスタンスを渡しているが、新しいオブジェクトとして再代入しても呼び出し元の変数には影響しない。、これはローカル変数の再代入でしかない。
   `inner2` が `f` に新しいクラスインスタンスを代入し直すと別のインスタンスが生成されるので、`outer` 内の `f` には反映されません。

1. 引数の値として `nil`/`null`/`None` を渡した場合、引数自身を新しい値に設定しても、呼び出し側の変数は変更されない

</Steps>

この振る舞いを説明するのに、こうした言語においてはクラスのインスタンスは "参照によって渡される" からと説明する人もいますが、それは正しくありません。
参照渡しであれば上記の `inner1` の直後の呼び出しの場合と `inner2` の直後の呼び出しの場合とで、呼び出し元の変数が変更されるはずです。

これらの言語も Go とまったく同じですべてが **「値渡し」** なのです。

この現象は、クラスのインスタンスがポインタとして実装されているからです。**インスタンスが関数やメソッドに渡される際にコピーされる値はインスタンスへのポインタ**です。

Go で ポインタ変数やポインタ引数を使っても、まったく同じ振る舞いが見られます。
Go がこれらの言語と違うのは、Go は基本型に対しても構造体に対しても、ポインタで渡すか値で渡すかの選択をさせてくれるという点です。たいていの場合は値で渡すべきです。
そうすればデータがいつどのように変更されたかがわかりやすくなります。

:::note[Go のポインタと構造体の扱い]

**一律の値渡し**

Go では、基本型（int、string など）も構造体も、デフォルトではすべてを「値渡し」で関数に渡します。つまり、渡された引数はコピーされるため、**関数内で変更しても元の値には影響しません。**

**ポインタ渡しの選択肢**

コピーにコストがかかる大きな構造体や、関数内で変更を反映させたい場合は、ポインタを使って渡すことができます。ポインタ渡しにすると、**関数には変数のアドレスがコピーされるので、関数内でそのアドレスを介して元の値を変更できます。**

推奨は値渡しです。
単純な基本型の場合、値渡しのほうが直感的でバグも起こりにくいため、通常は値渡しが好まれます。
また、明示的にポインタ渡しにすることで、どこで値が変更されるかがより明確になります。

まとめると、Go ではどの型に対しても、値渡しかポインタ渡しかを選択できる柔軟さがあり、基本型だけでなく構造体でも、必要に応じた使い分けが可能です。ほとんどの場合は、意図しない副作用を防ぐために値渡しを利用するのが望ましいという意味です。

:::

値渡しをすると、ガベージコレクタの仕事量が減るという利点もあります。

## ポインタはミュータブル(変更可能)の印

Go ではコンパイル時に計算されるリテラル式に定数として名前をつけることができます。
しかしその他の値がイミュータブル(変更不可能) であることを宣言する仕組みはありません。

[イミュータブル](/golang/base/11_golang-basic-type/#定数)

現代のソフトウェア工学はイミュータブルの効果を信奉しています。MIT の ["Software Construction"](https://web.mit.edu/6.031/www/fa20/classes/08-immutability/) では、その理由を次のようにまとめています。

> _イミュータブルな型はバグが起こりにくく、理解しやすく、変更しやすい。逆にミュータブル(変更可能)であるとプログラムが何をしているか理解しにくくなり、動作を保証するのが困難になる。_

Go ではイミュータブルを宣言できないことが問題だと思えるかもしれませんが、引数として値を渡すかポインタを渡すかを選択可能であることが問題解決の鍵になります。

"Software Construction" ではさらに次のように説明しています。

> _ミュータブル(変更可能)なオブジェクトを使っても、それが一つのメソッド内のローカルなもので、そのオブジェクトを参照するポインタが一つだけであるならまったく構わない。_

変数や引数がイミュータブルであると宣言する代わりに、Go ではポインタを使って引数がイミュータブルであることを示すのです。

### ポインタ渡し(=値渡し)

Go は値渡しの言語ですから、関数に渡される値はコピーです。基本型、構造体、配列といった非ポインタ型では、関数は元のデータを変更できないことになります。
呼び出される側の関数がもっているのは元データのコピーですから、元データがイミュータブルであることは保証されます。

:::caution[参照渡しではなく、ポインタ渡し(=値渡し)]

Go の関数は、値渡しですので、引数に渡された値はコピーされオリジナルの変更を防ぎます。
つまり、実質的にイミュータブルなように動作します。

変更が必要な場合はポインタ渡しを使用して、明示的にどのデータを変更するかを判断する仕組みをとります。
これは参照渡しのように見えますが、実際には値渡しです。
つまり、変数が参照するポインタの値をコピーして関数内に渡していますが、その値はポインタの値のため、オリジナルへの変更が反映されるのです。

:::

#### nil ポインタは更新できない

関数にポインタとして `nil` を渡した場合、その値を `nil` に変更することはできません。
値渡しで関数にメモリ内のアドレスを渡した場合、そのアドレスを変えることはできません。int の引数の値を変えることができないのと同じです。

```go
func failedUpdate(g *int) { // g は nil --②
	x := 10 // x は 10 --③
	g = &x // g は x のアドレス --④
}

func main() {
	var f *int // f は nil --①
	failedUpdate(f)
	fmt.Println(f) // <nil> --⑤
}
```

## ポインタは最後の手段

Go でポインタを使う際には慎重であるべきです。
前に述べたように、データの流れがわかりにくくなり、ガベージコレクタの仕事も増えます。関数にポインタを渡して構造体の中身を埋めるのでなく、関数が構造体のインスタンスを作成して返すようにします。

**悪い例**

```go
func MakeFoo(f *Foo) error {
    f.Field1 = "val"
    f.Field2 = 20
    return nil
}
```

問題点としては

- 関数に既存の Foo インスタンスのポインタを渡し、その内容を内部で変更している
- 呼び出し側がどこでどのように値が変わるのか追いにくく、データの流れが不明瞭になりやすい
- 副作用（関数の呼び出しによって外部の状態が変更される => デリファレンスによる変更）が発生するため、メンテナンス性やデバッグが難しくなる可能性があります

**良い例**

```go
func MakeFoo() (Foo, error) {
	f := Foo{
		Field1: "val",
		Field2: 20,
	}
	return f, nil
}
```

改善点を要約すると

- 関数自体が Foo インスタンスを新たに生成して返すため、呼び出し側は返り値として得たインスタンスを利用する。
- (↑ により)関数内でのデータの流れが明示的になり、副作用を避ける設計が実現されます。
- 新しい値を返すことで、既存のデータが予期せず変更されるリスクをなくし、コードの可読性と保守性が向上する。

変数を変更するのにポインタ引数を使わなくてはならないのは関数がインターフェースを受け取るだけの場合です。
JSON を扱う場合にこのパターンを出現します。

関数から値を返す場合は、ポインタではなく値として返すべきです。ポインタ型を返すのはデータ型の中に変更するべき状態がある時だけです。
[入出力](/docs/golang/base/20_standard-library/#入出力)で I/O を扱う際にはバッファを使ったデータの読み書きについて説明します。
さらに[並行実行](/docs/golang/base/19_concurrent-processing/)に使用されるデータ型も必ずポインタとして渡さねばなりません。

## ポインタ渡しのパフォーマンスについて

構造体のサイズが大きくなると、引数として渡す際にも戻り値として戻す際にもポインタを使った方がパフォーマンスがよくなります。

### ポインタ渡しの特性

- 関数にポインタを渡す時間は、データのサイズに依存せず一定（約 1 ナノ秒程度）です。これは、ポインタ自体が持つ情報（参照先のアドレス）が固定サイズ（通常 8 バイトなど）だからです。

### 値渡しの特性

ポインタを返す場合と、値を返す場合でパフォーマンスにどの程度の違いがあるかというと

- **1 メガバイトより小さいデータの場合、ポインタ型を返す方が値を返すより実際には遅い**  
  例えば、100 バイトのデータを返すのに 10 ナノ秒かかりますが、同じデータを参照するポインタを返すのに 30 ナノ秒かかります。
- 小さいデータの場合、コピー自体のコストは非常に低くなります。
- しかし、データサイズが大きくなると、そのコピーコストが無視できなくなり、転送に要する時間が増加します。
- 例えば、値のデータが 10 メガバイトほどの場合、コピーに約 1 ミリ秒程度かかるとされています。

**データの大きさが 1 メガバイトを超えると、パフォーマンスは逆転します。**
10 メガバイトのデータを返すのに 2 ミリ秒近くかかるのに対し、同じデータへのポインタを返すのには 0.5 ミリ秒しかかかりません。

## ゼロ値と値なし

Go でのポインタの使用法として一般的なのが、
プログラムの文脈によって変数やフィールドに「意図的にゼロ値を設定した(ゼロ値)」のか「値が設定されていない(値なし)」のかを区別したい場合があります。

そのため、ポインタを使って「値なし」を示すと、ゼロ値と区別しやすくなります。nil ポインタは「値が未設定」であることのサインになります。

### nil ポインタの利用と注意点

プログラム内でこの区別が問題となる場合に、「値なし」の変数や構造体フィールドを示すのに nil ポインタを使うのです。

nil はポインタが参照する先が存在しない状態を示します。nil に対してデリファレンスで値を代入することはできません。たとえば、関数の引数として nil を渡すと、その関数内でそのポインタに新しい値を設定（代入）しようとしても、nil はアドレスではないので変更できません。

nil のポインタをデリファレンスして値を代入しようとすると、ランタイムエラーが発生する例

```go
package main

import "fmt"

// updateValue は、受け取ったポインタが指す先に 100 を代入しようとします。
// もし、nil のポインタが渡された場合、*ptr にアクセスした時点で panic となります。
func updateValue(ptr *int) {
	*ptr = 100
}

func main() {
	var p *int // p は nil で初期化される（つまり有効なメモリアドレスを持たない）

	// nil のポインタ p を渡しているので、ここで updateValue 内の *ptr = 100 により panic が発生します。
	updateValue(p)

	fmt.Println("更新後の値:", p)
}
```

### ["カンマ ok イディオム"](/golang/base/12_golang-composite-type/#カンマ-ok-イディオム) の活用

関数から結果を返す際に、nil かどうかを返すより、値とブール値をセットで返す「カンマ ok イディオム」を使う方が明確です。

ポインタはミュータブル(変更可能)であることを表すのにも使いますから、このパターンを使うときには注意して使いましょう。
関数から nil に設定したポインタを返すのではなく、["カンマ ok イディオム"](/golang/base/12_golang-composite-type/#カンマ-ok-イディオム)を使い、値とブール値を返すようにします。

呼び出し側は「値が存在するかどうか」を明示的に確認できます。

```go
// Map から値を取得する場合のカンマ ok イディオム
value, ok := myMap[key]
if !ok {
    // 値が存在しなかった場合の処理
}
```

引数として nil を渡したり、引数として渡した構造体のフィールドに nil があったりした場合、関数内ではそこに値を設定できないことを覚えておきましょう。
nil はアドレスではないので値を代入できません。ポインタとして nil でない値を渡す場合、それを変更するならば、その旨をドキュメントに記載しましょう。

### 関数とポインタ渡しの挙動

関数にポインタを渡すと、そのポインタの値（アドレス）がコピーされます。
関数内でそのコピー先を デリファレンス して値を変更すれば、元の変数も変わります。
しかし、渡されたポインタ変数そのもの（アドレスそのもの）を再代入しても、呼び出し側の変数には影響しません。

### ドキュメントの重要性

ポインタを用いてミュータブル（変更可能）な状態をどこで、どのように変更するかは明確に記録する必要があります。
たとえば、nil でない有効なポインタを渡し、そのポインタの指す値を関数内で変更する場合は、
その旨をドキュメントで説明することで、利用者が副作用を正しく理解できます。

### JSON の変換について

データを JSON とやりとりする場合、「ゼロ値」と「値なし」の区別が重要です。
「値なし」に設定できる構造体フィールドにはポインタ値を使いましょう。

JSON (あるいはその他の外部プロトコル)を使っているのでなければ、「値なし」を示すのにポインタのフィールドを使いたくなっても我慢しましょう。
ポインタは「値なし」を示すのに便利に思えるかもしれませんが、値を変更するのでなければ、代わりに「値型とブール値のペア」を使うべきです。

## マップとスライスの違い

関数に渡されたマップに対する変更は元のマップに反映されます。[参考](/golang/base/14_function/#マップの場合)  
Go では、マップは構造体へのポインタとして実装されています。関数にマップを渡すということは、ポインタをコピーするということです。

```go
func updateMap(m map[string]int) {
	m["key"] = 100 // ここで m は、元の map を指すポインタのコピーです。
	// m["key"] に代入すると、実体である map の内容が更新されます。
}

func main() {
	original := map[string]int{"initial": 0}
	updateMap(original)
	// original["key"] は 100 に更新されている
	fmt.Println(original) // 出力: map[initial:0 key:100]
}
```

そのため、マップを入力用のパラメータに使ったり、値を返すのに使ったりすることは避けねばなりません。
これは特に公開 API で言えることです。API 設計のレベルでは、マップは中身の値について何も言えないため、良い選択肢ではありません。

### マップをパラメータや戻り値に使う問題点

#### API の明示性が低い

マップはキーと値のペアを格納するデータ型です。マップにどんなキーがあるのかを明示的に型レベルで定義するものがないので、キーを知りたければコードを読むしかありません。つまり、API の利用者は「どのキーが存在し、どんな意味を持つのか」を知るのに、ドキュメントや実装コードを逐一確認する必要があり、直感的に理解しづらい設計になりがちです。
イミュータブル(変更不可)を重視する立場から言えば、マップの内容がどうなるかは、マップに関係する関数のコードをすべて読んでみるしかないのでやはり良くないということになります。

API が「見ればわかる」ものでなくなってしまいます。

#### 型安全性の低下

動的言語に慣れていても、他の言語の仕組みの代用にマップを使ってはなりません。Go は強い型付けの言語です。マップを渡すのではなく構造体を使いましょう。
構造体を使えば、フィールド名や型が明示されるため、どの値がどこに入るべきかがコンパイル時にチェックできます。

マップの場合、キーはただの string 型になることが多く、値の型も `interface{}` にしてしまえば柔軟性はあるものの、どんな値が入るか利用者が推測するしかなく、型安全性が低下します。

#### 不透明な内部状態

マップに対する変更は、その内部データにアクセスして変更する形となるため、外部からは「どの部分がどのように変更されたか」が追いにくくなります。  
公開 API であれば、明示的な構造体で定義し、更新可能な部分と不変の部分を分けるなど、意図が明確になる設計を行うべきです。

#### 保守性と将来の拡張

マップでは、たとえば追加のキーが参入した場合の型チェックがされないため、後からコードを変更する際に、どの部分に影響が出るかを全体的に確認しなければならなくなります。逆に構造体であれば、フィールド追加時にその影響範囲が明確になるので、メンテナンス性が向上します。

:::tip[推奨される設計]

Go の公開 API ではマップを直接渡すのではなく、構造体を使う設計が推奨されています。

- **入力値や出力としての構造体の利用**

  API 設計では、明示的な構造体を使い、各フィールドでどのような内容を扱うかを明確にしましょう。
  こうすることで、利用者は API の仕様を「見ればわかる」状態にでき、コードレビューや保守時にもメリットがあります。

- **型安全な API 設計**

  必要な場合は、構造体のフィールドに対してコメントやドキュメントを付与し、どんな値が期待され、どのような意味を持つのかを明示します。

:::

なお、[「ガベージコレクタの負荷軽減策」](#ガベージコレクタの負荷軽減策)でメモリレイアウトについて説明する際に、構造体を使った方が良い理由がもう一つ出てきます。

構造体は、メモリレイアウトが明示的に定義されているため、ガベージコレクタ（GC）側でも「どのフィールドがどこにあるか」が把握しやすいです。
一方で、マップは内部的にはポインタのコピーを渡している状態であり、メモリ管理のオーバーヘッドも発生しやすく、特に大規模なデータ操作が行われる場合にパフォーマンスの低下要因になることがあります。

## バッファとして使うスライス

ファイルやネットワーク接続といった外部リソースからデータを読み込む際、多くの言語では次のようなコードを使います。

```go
r = open_resource()
while r.has_data(){ // r にデータがある限り
  data_chunk = r.next_chunk() // data_chunk にデータを読み込む
  process(data_chunk) // 読み込んだデータを処理する
}
```

このコードは、データの読み込みが完了するまでデータを読み込み続けます。

このパターンの問題は、1 回しか使われない `data_chunk` を `while` ループを回るたびに新たに割り当てることです。おかげで不必要なメモリは自動的に処理されるとはいうものの、読み込みが終わった後に処理が必要であることに変わりはありません。

Go にもガベージコレクションはありますが、不必要なメモリ割り当てを避けると決まった「イディオム」があります。
データソースから読み込むたびに新たにメモリ割り当てをするのではなく、バイトのスライスを一度だけ作成し、それをデータソースからデータを読み込むバッファとして用いるのです。

```go
file, err := os.Open("file.txt")
if err != nil {
  log.Fatal(err)
  return err
}

defer file.Close()

data := make([]byte, 100)

for {
  count, err := file.Read(data)
  if err != nil {
    return err
  }
  if count == 0 {
    return nil
  }
  process(data[:count])
}
```

関数にスライスを渡した時に長さやキャパシティは変えられないと説明しましたが、内容は端から端まで変えることができます。上のコードでは 100 バイトのバッファを作成し、ループを回るたびに次のブロック(最高 100 バイト) をスライスにコピーしています。
それからデータを入れたいバッファをデータの入っているところまで process に渡します。このような I/O 関連の処理については[入出力](/golang/base/20_standard-library/#入出力)で詳しく説明します。

## ガベージコレクタの負荷軽減策

### ガベージ(garbage)とは

ここで言う「ガベージ」とは、**どのポインタからも参照されなくなったデータ**のことです。参照がなくなると、そのメモリ領域はシステムによって回収され、他の目的に再利用されます。
もしガベージの回収が適切に行われなければ、プログラム内でメモリ使用量がどんどん増えてしまい、最悪の場合、RAM の枯渇につながります。

#### ガベージコレクタの役割

ガベージコレクタは、**プログラム実行中に不要になったメモリ領域を自動的に検出し、再利用のために回収する仕組み**です。
Go の GC は、こうしたメモリ管理を自動化することで、開発者が低レベルなメモリ管理から解放されるように設計されています。ただし、ガベージを大量に作ってしまうと GC の負荷が高くなり、パフォーマンスに影響を与える可能性があります。

#### バッファを利用したガベージコレクタの負荷軽減策

バッファ（例えば、固定サイズのスライス）を使ってデータを一度だけ割り当て、それを再利用することで、読み込みや処理のたびに新たなメモリ割り当てを避けられるため、不要なガベージ生成を減らし、GC(ガベージコレクタ) の負荷を軽減する狙いがあります。

:::tip[ヒープとスタック]

ヒープとは、プログラムの実行中に動的にメモリが割り当てられる領域のことです。以下のポイントで説明できます。

- 動的確保されたメモリ領域

  必要に応じて実行時にメモリが確保され、確保されたメモリは利用期間が不定となります。たとえば、`new` や `malloc` などの関数で確保されるメモリがヒープに割り当てられます。

- ガベージコレクションとの関係

  Go のような言語では、ヒープ上のメモリはガベージコレクタによって管理され、すべての参照がなくなった不要なデータ（ガベージ）は自動的に回収されます。これにより、プログラマは明示的な解放を行わなくても済む仕組みになっています。

- スタックとの違い

  スタックは関数呼び出しごとに割り当てられる短命なメモリ領域で、自動的に解放されます。一方、ヒープは長期間必要となるような大規模データや、動的にサイズが変化するデータなどに使用され、メモリの解放方法は言語や実装に依存します。

まとめると、ヒープは動的にメモリ確保を行い、必要なくなったときにガベージコレクタなどで回収される、実行時に柔軟に利用されるメモリ領域です。

### スタックによるメモリ管理

#### スタックの基本概念

スタックは、関数呼び出しごとの「スタックフレーム」として使われ、ローカル変数や関数引数を格納するメモリ領域です。
スタック割り当ては非常に高速で、スタックポインタを単に上下させるだけでメモリの確保や解放が行われます。

#### スタックポインタとスタックフレーム

メモリを割り当てるとき、現在のスタックポインタの位置が保存され、新しい変数分だけスタックポインタが移動します。
関数呼び出しにより新しいスタックフレームが作られ、その中にローカル変数や引数が格納されます。
関数の実行が終了すると、戻り値はスタック上で呼び出し元に返され、スタックポインタは元の位置まで戻されます。このとき、対応するスタックフレームで確保されたメモリは解放されます。

プログラミング言語の実装について学んだことがある人なら、「ヒープ」と「スタック」についても学んだと思いますが、ここではよく知らない人のためにスタックがどう使われるかを説明しましょう。スタックは一連のメモリブロックで、実行されるスレッドのすべての関数呼び出しが同じスタックを共有します。
スタック上のメモリ割り当ては高速で単純です。
メモリを最後に割り当てた位置は「スタックポインタ」に保存され、追加でメモリを割り当てる際にはスタックポインタを動かすことで割り当てます。
関数が呼び出されると、その関数のデータのために、新たに「スタックフレーム」が生成されます。ローカル変数は、関数に渡された引数とともに、このスタック上に保存されます。新しい変数が定義されるたびにスタックポインタはその変数の値のサイズの分だけ動かされます。関数が終了すると戻り値がスタック経由で呼び出し元の関数に返され、終了した関数のスタックフレームの最初の位置までスタックポインタが戻されることで、その関数のローカル変数や引数に使用されていたスタック上のメモリがすべて解放されます。
