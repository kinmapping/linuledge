## CSRF とは

CSRF（Cross-Site Request Forgery、クロスサイトリクエストフォージェリ）は、Web アプリケーションのセキュリティ三大脆弱性の一つです。攻撃者がユーザーのブラウザを介して、ユーザーが意図しない操作を、信頼しているウェブサイト上で実行させられるといった攻撃です。

CSRF 攻撃は、以下のようなメカニズムで行われます。

### 攻撃の前提条件

- **ユーザーの認証状態**  
  攻撃対象のサイトにユーザーがログインしており、セッション情報（例：クッキー）がブラウザに保持されていることが前提です。この状態では、ユーザーはそのサイトに対して正当なリクエストを送れる状態になっています。

- **脆弱なウェブサイト**  
  対象のウェブサイトが CSRF 対策（例：CSRF トークンの実装）をしていない、または十分でない場合、攻撃が成立しやすくなります。

### 攻撃の流れ

1. **ユーザーの認証状態の利用**  
   ユーザーが攻撃対象のウェブサイトにログインしており、認証情報（セッション ID など）がブラウザに保存されている状態です。

2. **悪意のあるサイトやメールの仕掛け**  
   攻撃者は、ユーザーを悪意のあるウェブページ、電子メール、またはチャットなどに誘導します。([ユーザーの誘導手段](#ユーザーの誘導手段))
   このページには、攻撃対象のサイトへリクエストを送るための仕掛けが仕込まれています。

3. **リクエストの自動送信**  
   悪意のあるページには、以下のような方法で攻撃対象サイトに対するリクエストが埋め込まれています。

   - **HTML フォームの自動送信**  
     ユーザーがページを開くだけで、隠しフィールドに必要な情報を持つフォームが自動的に送信され、攻撃対象サイト上で操作が実行される。
   - **画像タグの利用**  
     `<img src="http://vulnerable-site.com/action?param=value">` のように、画像リクエストとして攻撃対象サイトへリクエストを送る手法。
   - **JavaScript によるリクエスト送信**  
     被害者のブラウザが自動的にリクエストを発行するようにスクリプトが組み込まれている場合。

4. **攻撃対象サイトでのリクエスト受理**  
   ユーザーのブラウザは既にログイン状態であるため、攻撃対象のサイトはリクエストを正当なユーザーからのものとして処理してしまいます。結果として、ユーザーの意思に反した操作（例えば、送金処理、パスワード変更、設定の変更など）が実行されることになります。

#### ユーザーの誘導手段

##### フィッシングメール

ユーザーに信頼できる組織（例えば銀行やショッピングサイト）からのメールと偽装し、アカウントの確認やキャンペーン情報、セキュリティ警告などを装ってリンクをクリックさせます。

例.

- 「あなたのアカウントに不審なアクセスがあります。こちらのリンクからすぐに確認してください」という内容のメールに、攻撃者が管理する悪意のあるサイトへのリンクが埋め込まれている。

##### ソーシャルメディア、チャット、メッセージアプリ

SNS、メッセージングアプリ、掲示板などで、信頼されやすい情報（ニュース、キャンペーン、友人からのメッセージなど）として偽装したリンクを投稿・送信します。

例.

- 「限定オファーはこちら！」といった投稿や、友人になりすましたアカウントからのダイレクトメッセージに、悪意あるリンクが含まれている。

##### 悪意のあるサイト

攻撃者が作成したウェブサイトや広告ページに誘導し、ページが表示されるだけでバックグラウンドで攻撃が実行されるように仕掛ける場合です。

例.

無料ダウンロード、コンテスト応募、キャンペーン参加などの見た目は魅力的なページに誘導し、ユーザーが何かアクションを起こす（または単にページを表示する）と自動的に攻撃リクエストが発行される。

---

#### 攻撃対象のサイトへリクエストを送るための仕掛け

攻撃者は、ユーザーが誘導された先のページに以下のようなコードや仕組みを仕込むことで、ユーザーのブラウザから攻撃対象のサイトへ不正なリクエストを送信させます。(リクエストの URL やパラメータがクリティカルな場合は、これらの仕組みを利用して攻撃が成立する可能性があります。)

##### フォームの自動送信

隠しフィールドに必要なパラメータを設定したフォームをページ内に用意し、JavaScript で自動送信する方法です。

```html
<!-- vulnerable-site.com は攻撃対象のサイト -->
<form id="csrfForm" action="http://vulnerable-site.com/transfer" method="POST">
  <input type="hidden" name="amount" value="1000" />
  <input type="hidden" name="toAccount" value="attacker_account" />
</form>
<script>
  document.getElementById("csrfForm").submit();
</script>
```

ユーザーがこのページをレンダリングしたと同時にフォームの自動送信が行われます。ユーザーの認証情報(Cookie など)を伴ってリクエストが攻撃対象のサイトに送信されます。

##### 画像タグ`<img>`の利用

画像タグの src 属性に、攻撃対象サイトへのリクエスト URL を指定することで、ブラウザが自動的にその URL へ GET リクエストを送信させます。

```html
<img src="http://vulnerable-site.com/deleteAccount?confirm=true" alt="" style="display:none;" />
```

画像の読み込みエラーが発生してもユーザーには気付かれず、GET リクエストが発行されるため、ログアウトやアカウント削除などの操作が実行される可能性があります。

##### JavaScript による非同期リクエスト (AJAX/Fetch API)

JavaScript を使用して、 `XMLHttpRequest` や `fetch` 関数で攻撃対象の URL へリクエストを送信します。これにより、POST リクエストやカスタムヘッダー付きのリクエストも可能です。

```html
<script>
  fetch("http://vulnerable-site.com/updateEmail", {
    method: "POST",
    credentials: "include", // クッキーを送信するためのオプション
    headers: {
      "Content-Type": "application/x-www-form-urlencoded",
    },
    body: "email=attacker@example.com",
  });
</script>
```

JavaScript の`fetch`関数により、ユーザーの認証情報（`credentials: 'include'` によりクッキーなど）が含まれた状態でリクエストが送信され、被害者の意図しない操作（ここではメールアドレスの変更など）が実行される可能性があります。

### 攻撃の実例

- **銀行サイトの場合**  
  被害者がオンラインバンキングにログインしている状態で、攻撃者が送ったメール内のリンクや仕込まれた画像リクエストにより、ユーザーの資金が攻撃者の口座に送金される可能性があります。

- **ソーシャルメディアの場合**  
  ユーザーがログイン中の状態で、攻撃者が投稿やリンクを介して、意図しない友達リクエストやメッセージ送信などのアクションを強制することがあります。

### 防御策

防御策には以下のような方法があります。

- **CSRF トークンの導入**: トークンによるリクエストの正当性検証
- **SameSite Cookie 属性の設定**: 他サイトからの Cookie の送信を防ぐ
- **リファラーチェック**: リクエストの発生元を確認する
- **ユーザーの確認**: 高リスクな操作の場合はユーザーの確認(多要素認証など)を求める

#### CSRF トークンの導入

各リクエストに対して、一意で予測不可能なトークンを発行し、そのトークンが一致しないリクエストを拒否する方法です。
攻撃者が対象のサイトに悪意のあるリクエストを実行する方法は、攻撃者が管理しているサイトからです。そのため、防御策を図るサイトでは、サーバーで任意のトークンを発行し、ユーザーのセッションに関連づけることで、防御策を図るサイト自身でのリクエストは信頼性を担保するリクエストとして処理することができる。悪意のあるサイトでは、そのトークンを予測することができないため、リクエストが成立しないような仕組みを作ることで防御策を図ることができます。

##### トークンの発行と埋め込み

- **トークンの発行**

  ユーザーがフォームページをリクエストすると、サーバーはランダムで予測不可能な文字列（CSRF トークン）を生成し、ユーザーのセッションに保存します。

- **トークンの埋め込み**

  生成したトークンは、HTML フォームの hidden フィールドや、AJAX リクエストのヘッダーに埋め込まれ、クライアント側に送信されます。

- **リクエスト時のトークン送信と検証**

  1. フォームの送信時に、CSRF トークンがリクエストの一部としてサーバーに送られます。

  1. サーバーはリクエストに埋め込まれたトークンとユーザーのセッションに保存されたトークンを比較します。

  1. 一致しない場合はリクエストを拒否する。一致する場合は、リクエストは正当であると判断し、通常の処理が続行されます。

:::tip[リクエストの拒否方法]

- **エラーレスポンスの返却**

  不正なリクエストが検出された場合は、サーバーは HTTP 403 Forbidden エラーやカスタムエラーメッセージを返して処理を中断する

- **ログの記録**

  多くの場合、セキュリティログに不正な試みが記録され、管理者に通知されることがあります。

:::

##### SameSite の具体的な設定手順

HTTP レスポンスヘッダーでクッキーを設定する場合、以下のように指定できます。

- Strict の場合

  ```http
  Set-Cookie: sessionid=abc123; SameSite=Strict; Secure; HttpOnly
  ```

  sessionid クッキーは同一サイト内のリクエストでのみ送信され、外部サイトからのリクエストではブラウザが自動的に除外します。

- Lax の場合

  ```http
  Set-Cookie: sessionid=abc123; SameSite=Lax; Secure; HttpOnly
  ```

  この設定では、トップレベルナビゲーションの GET リクエストにはクッキーが送信されますが、フォーム送信や AJAX リクエストなど、状態変更のリクエストにはクッキーが送信されないため、CSRF 攻撃のリスクを軽減します。

Cookie ファイルの送信制御を行うことで、悪意のあるサイトからのリクエストに認証情報を付与できないようにすることができます。SameSite=Strict(や Lax) を設定していると、ブラウザは自動的にクッキー（セッション情報など）を添付しません。その結果、攻撃対象サイトはリクエストを認証済みのものとみなさず、不正な操作を防止できます。

これで、ユーザー認証状態を悪用した攻撃を防ぐことができます。
正当なユーザーが直接サイトにアクセスする場合のみクッキーが送信されるため、攻撃者が意図しないリクエストを強制的に実行できなくなります。

#### リファラーチェック

HTTP リクエストの発生元（Referer ヘッダー(参照元)）を確認し、正当なドメインからのアクセスかどうかを検証する方法。
具体的には、サーバーが受信したリクエストの Referer を読み取り、その値が自サイトのドメインまたは、許可されたドメインのものか確認します。許可できるドメインでは、リクエストを許可し、許可できないドメインではリクエストを拒否します。

##### 具体的な実装(PHP)

例えば、PHP でのサーバー側の処理は以下のようになります。

```php

// 許可するドメイン（自サイトのドメインなど）
$allowed_domain = 'example.com';

// リクエストにRefererが含まれているかチェック
if (!isset($_SERVER['HTTP_REFERER'])) {
    http_response_code(403);
    exit('不正なリクエストです。');
}

// Refererからホスト名を抽出
$referer_host = parse_url($_SERVER['HTTP_REFERER'], PHP_URL_HOST);

// 許可ドメインと一致するか検証
if ($referer_host !== $allowed_domain) {
    http_response_code(403);
    exit('不正なリクエストです。');
}

// ここから正当なリクエストとして処理を続行
echo "リクエストは正当なものとして処理されます。";
```

リファラーチェックには、リクエスト送信元のドメイン検証という意味があります。攻撃者による不正なリクエストを検知し、ブロックできます。また補助的な防御策となりますので、他の防御策と掛け合わせて利用することが考えられます。
Cookie の不正利用を防ぐという SameSite 属性との掛け合いで、
さらに、防御レベルを高めることができますし、
CSRF トークンが読み取られてしまい、セッション情報を上書きすることができてしまったとしても、Referer ヘッダーが自サイトのドメインであることを確認することで、不正なリクエストをブロックできます。

:::caution[Referer ヘッダーの注意点]

- **Referer の欠如**

  Referer ヘッダーは、ブラウザの設定によっては送信されない場合があります。
  ユーザーのブラウザ設定や一部のプライバシー保護ソフト、企業のネットワーク環境などでは、
  Referer ヘッダーが送信されないことにより、正当なリクエストであっても拒否される可能性があります。

- **改竄の可能性**

  Referer ヘッダーは、クライアント側で操作可能なため、攻撃者が偽の Referer を送信する可能性があります。
  したがって、リファラーチェックは CSRF トークンなど他の対策と併用することが推奨されます。

- **あくまで補助的な防御策**

  Referer ヘッダーは、あくまで補助的な防御策です。
  他の複数の防御策（CSRF トークン、SameSite Cookie など）と組み合わせて利用することで、より安全なウェブアプリケーションを構築できます。

実装時には、正当なリクエストまでブロックしないように、また攻撃者による偽装に対しても他のセキュリティ対策と併用することが重要です。

:::

#### ユーザーの確認

高リスクな操作（パスワード変更、送金など）の場合は、再度パスワード入力や二要素認証を要求するなどの確認を行う。

以下のような確認操作が挙げられます。

- **再認証**

  高リスクな操作（パスワード変更、送金など）の際に、現在のパスワードや PIN の再入力を求める方法。

- **多要素認証**

  ワンタイムパスコード（OTP）や認証アプリ、SMS、ハードウェアトークンなど、複数の認証要素を組み合わせることで本人確認を強化する方法。

- **CAPTCHA**

  ユーザーがロボットではない(自動化された操作)ことを確認するための画像や音声などのチャレンジを出題し、ユーザーが正答することで本人確認を行う方法。

### ミドルウェアでの処理

これらの認証には、web フレームワーク側のミドルウェアやプラグインで処理します。

---

### まとめ

CSRF 攻撃は、ユーザーの認証状態を悪用して意図しないリクエストを送信させる攻撃手法です。攻撃者は、悪意のあるコンテンツを通じてユーザーのブラウザに攻撃対象サイトへのリクエストを自動的に送らせ、結果として不正な操作を実行させることが可能となります。適切な防御策を講じることで、このような攻撃からウェブアプリケーションを保護することが重要です。
